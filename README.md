# 社媒内容生产流程管理系统

> Social Content Workflow & Performance Tracker

一个面向海外市场社媒内容运营的流程管理与效果复盘工具。

---

## 一、项目背景

在海外市场的社媒内容运营中,一条内容从选题到发布通常要经过 7 个环节,涉及素材提供方、多位审核人、多个发布平台。在实际工作中,有两个环节最容易造成阻塞:

**素材等待。** 文案和脚本完成后,往往需要等待同事或海外团队提供拍摄素材才能进入制作环节。等待过程缺乏记录,导致无法回答"这条内容卡了多久""在等谁""催过几次"这类问题,只能笼统地说"还在等素材"。

**审核返工。** 内容需要经过老板(方向审核)、同事/mentor(质量审核)、英语母语者(语言与本地化审核)三个角色的审核,任何一轮打回都需要重新导出文件、上传、发送给审核人,流程繁琐。更关键的是返工历史没有留存,同类问题会被反复提出,也无法判断返工究竟集中在哪个原因上。

现有的 Excel 排期表只能记录"内容是什么",无法回答"内容卡在哪里、卡了多久、为什么反复返工"。

本项目的目标不是做一个内容记录表,而是做一个**能暴露流程瓶颈、并支持数据驱动复盘的工具**:前半段解决生产阻塞问题,后半段解决内容策略优化问题。

## 二、核心功能

### 1. 内容录入与管理

按内容生命周期的三个阶段组织字段:

**计划阶段**

| 字段 | 说明 |
|---|---|
| 计划发布日期 | |
| 发布平台 | Facebook / Instagram / LinkedIn / YouTube |
| 选题 | |
| 内容类型 | 产品卖点 / 应用场景 / 用户教育 / 客户案例 / 活动预告 / 行业热点 |
| 内容形式 | 图文 / 短视频 / Reels / 长视频 / 轮播图 / Story |
| 内容目标 | 品牌曝光 / 用户教育 / 线索转化 / 活动引流 |
| 关联 Campaign | 新品推广 / 展会宣传 / 季节性节点 / 行业热点 |
| 语言与目标市场 | |
| 负责人 | |

**制作阶段**

| 字段 | 说明 |
|---|---|
| 文案 | |
| 素材来源 | 记录素材提供方,用于追踪等待时长(素材"状态"通过下面的状态流转追踪,不是单独字段) |
| 当前状态 | 见状态流转 |
| 进入当前状态的时间 | 用于计算阻塞时长 |
| 当前责任人 | 明确当前环节卡在谁那里 |
| 是否投放推流 / 投放金额 | 数据模型里已有这两个字段(数据库、种子数据都在用),**但录入表单目前还没开放这两项的填写入口**,是已知的待补项,见「后续规划」 |

**复盘阶段**

| 字段 | 说明 |
|---|---|
| 实际发布时间 | |
| 发布链接 | |
| 曝光量 | 作为互动率计算的分母 |
| 点赞 / 评论 / 转发 / 收藏 | 不同平台能采集到的指标不同(比如收藏在部分平台不存在),表单里对应字段允许留空,不会被当成 0 |
| 私信数 | |
| 涨粉数 | |
| 数据抓取时间 | 同一条内容在不同时间点的数据不可直接比较;每次更新复盘数据都会刷新这个时间戳 |

> 说明:曝光量作为独立字段的原因是,互动数据脱离曝光量无法横向比较。1000 曝光下的 50 个赞与 10 万曝光下的 50 个赞是完全不同的结果。复盘数据只有内容处于"发布"状态时才能填写,支持反复打开、覆盖式更新(比如发布 24 小时后填一次、7 天后再补一次)。

### 2. 状态流转与阻塞追踪

内容生产的 7 个环节:

```
选题 → 收集素材 → 写文案 → 制作 → 审核 → 排期 → 发布
  ↑___________________________|
  (审核可退回选题/收集素材/写文案/制作中的任意环节;
   正常推进允许跳级,比如"选题"可以直接跳到"写文案")
```

状态变化规则:往后走(推进)可以跳级,不限定只能走到相邻的下一步;往前走(回退)只有"审核"环节能触发,可以退回它之前的任意环节,其余环节一律不允许倒退;"发布"是终点,之后不能再变。每次变化都会在状态历史里记一条,并标记类型是"正常推进"还是"审核回退",供看板统计用。

系统在状态流转基础上追踪三项信息:

- **停留时长**:进入当前状态的天数,超过阈值(默认 3 天)标记为阻塞,已发布的内容不计入
- **当前责任人**:明确阻塞发生在哪个角色,而非笼统的"进行中"
- **回退记录**:每次状态变化(推进或回退)都在状态历史表里留一条记录,包含从哪个状态到哪个状态、谁操作的、什么时间。回退可以通过详情页手动触发,也可以在提交审核打回时自动联动触发——后一种情况会同时生成一条审核记录,前一种不会

### 3. 多角色审核与返工记录

审核由三个角色分别进行,关注维度不同:

| 审核角色 | 关注维度 |
|---|---|
| 老板 | 内容方向、是否可用 |
| 同事 / mentor | 内容质量、结构 |
| 英语母语者 | 语言准确性、本地化表达 |

打回原因分为五类:

1. **语言准确性** —— 语法、拼写错误
2. **本地化表达** —— 表达不够 local、翻译腔
3. **受众适配** —— 内容风格与目标受众(中老年用户)不匹配
4. **视听呈现** —— 配乐、画面节奏、字幕问题
5. **内容结构** —— 冗余、逻辑不顺

每条审核记录包含:审核人角色 / 审核人姓名(角色只有三类,但同一角色可能是不同的人,需要区分是谁提的意见) / 第几轮(系统自动计数,不用手填) / 审核结果(通过/打回) / 打回原因(**可多选**,同一轮反馈经常同时指出多个问题) / 具体意见 / 时间。同一条内容的多条审核记录构成完整返工历史。

> 提交范围说明:审核记录不是只能在"审核"环节提交——语言审核(英语母语者)经常在"写文案""制作"阶段就提前审一遍,所以这三个环节都能提交审核记录。但只有内容真正处于"审核"环节时,打回才会联动触发状态回退(退到哪个环节由提交人指定);提前审核的打回只记录问题,不会让流程往回走。

> 设计意图:打回原因分类的价值在于形成统计结论。若"受众适配"类打回占比过高,说明问题不在制作执行,而在选题阶段缺少受众对齐环节 —— 这类结论可直接转化为流程改进建议。

### 4. 数据看板

| 指标 | 展示形式 | 用途 |
|---|---|---|
| 当前阻塞内容数 / 平均审核轮次 | 大数字卡片 | 实时统计(不是"本周"这种时间窗口快照),一眼看到两个最关键的健康度指标 |
| 阻塞环节分布 | 条形图 | 定位最常见的瓶颈环节 |
| 打回原因分布 | 条形图 | 定位返工的根本原因 |
| 各内容目标效果 | 表格 | **按内容目标分组比较**(不分平台)—— 目标为曝光的内容比曝光,目标为转化的内容比私信数 |
| 平台效率对比 | 表格 | **按"平台 × 内容目标"交叉分组**,回答"同样类型的内容,发在不同平台上效果差多少";每组标注样本数,样本数低于 3 会提示"数据不足,仅供参考" |
| 素材等待统计 | 条形图(两组) | 只统计"收集素材"环节,按素材来源分组。"已完成等待"(平均天数+样本量提示)和"进行中等待"(当前条数+最长天数)分开展示,不合并,避免掩盖还在拖的问题 |
| 发布节奏(按平台) | 条形图 | 计划发布数 vs 已发布数的完成率 |

> 设计意图:内容效果不能用统一指标横向比较。一条以品牌曝光为目标的内容和一条以线索转化为目标的内容,评估标准本就不同。因此系统在录入阶段即要求指定内容目标,统计时按目标分组比较。"各内容目标效果"和"平台效率对比"这类多指标密集对比保留表格形式,不强行做成图表——指标之间数量级差异大、且分组样本量普遍偏小,图表反而容易让人过度解读不可靠的小样本差异。

### 5. 导入导出

- **CSV 批量导入**:批量导入内容的计划阶段字段(选题、平台、内容类型等,不含审核记录和复盘数据这些系统运行过程中才产生的数据)。提供模板下载,逐行独立校验,导入结果用"总数/成功/失败"汇总面板 + 失败行明细展示,不是逐条弹提示。同时处理了 Excel 导出 CSV 常见的编码问题(UTF-8 带 BOM、中文版 Excel 默认的 GBK)。
- **CSV 导出**:内容列表页导出当前筛选结果(字段比页面表格更全,含复盘数据和阻塞天数,方便整理排期表);数据看板页导出全部统计指标(阻塞分布、打回原因、各内容目标效果、平台效率对比、素材等待统计、发布节奏拼成一份文件)。导出内容都是"当前看到的数据"的完整版,不是另外做了周报/月报这种按日期区间取数的报表功能。

## 三、运行方式

### 环境要求

- Node.js 18 及以上版本(含 npm)

### 启动步骤

```bash
# 1. 安装依赖(根目录执行一次,前后端依赖会一起装好)
npm install

# 2. 一条命令同时启动前端和后端
npm run dev
```

启动后:

- 前端页面:http://localhost:5173
- 后端接口:http://localhost:4000
- 首次启动会自动在 `backend/data/` 下创建 SQLite 数据库文件并建好表结构,无需手动初始化。

### 灌入示例数据(可选)

想直接看到一个有内容的看板效果,而不是从空数据库开始手动一条条录入,可以跑一次种子数据脚本:

```bash
npm run seed -w backend
```

会先清空业务数据、再插入一批虚构的示例内容(约 28 条,覆盖不同平台/状态/内容目标,部分带审核打回记录),可以反复执行。所有数据均为虚构,不含任何真实公司、人物或商业数据。

## 四、技术栈

- 前端:React 18 + TypeScript + Vite
- 后端:Node.js + Express + TypeScript
- 数据库:SQLite(通过 better-sqlite3 直接读写本地文件,无需额外安装数据库服务)
- CSV 处理:csv-parse(解析,正确处理带逗号/引号的字段)+ iconv-lite(GBK 编码解码)—— 数据正确性相关的依赖,跟"能不装就不装"的原则不同,详见「AI 辅助开发过程」
- 开发工具:npm workspaces(统一管理前后端依赖)+ concurrently(一条命令同时启动前后端)
- 前端没有引入路由库或图表库:页面切换用简单的状态切换代替(避免引入有已知漏洞的 react-router-dom),看板的条形图是纯 CSS/SVG 手写实现

## 五、项目结构

```
social-content-tracker/
├── package.json           # 根目录脚本:一条命令同时启动前后端
├── backend/                # 后端:Express + TypeScript
│   ├── src/
│   │   ├── db/              # 数据库连接(建表逻辑就在连接建立时执行,schema.sql)、种子数据脚本(seed.ts)
│   │   ├── routes/          # 路由:定义有哪些接口
│   │   ├── controllers/     # 接收请求、返回响应(content/review/dashboard/import 四组)
│   │   ├── services/        # 业务逻辑:contentService(增删查)、statusService(状态机+阻塞天数)、
│   │   │                     #          reviewService(审核)、dashboardService(看板聚合统计)、importService(CSV导入)
│   │   ├── constants/       # 下拉选项常量(平台/内容类型等),与前端保持同步
│   │   └── types/           # TypeScript 类型定义
│   └── data/                 # SQLite 数据库文件(不进 git)
└── frontend/                # 前端:React + TypeScript + Vite
    └── src/
        ├── pages/            # 页面:录入/批量导入/列表/详情/看板
        ├── components/       # 可复用的界面部件(FilterBar、BarList 条形图)
        ├── api/              # 统一管理"向后端请求数据"的代码
        ├── utils/            # statusRules(状态机规则的前端镜像)、csv(CSV生成与下载)
        ├── constants/        # 下拉选项常量,与后端保持同步
        └── types/            # TypeScript 类型定义(与后端保持一致)
```

前后端分离架构:前端负责界面展示与交互,后端负责数据存取与业务逻辑,两者通过 HTTP 接口(`/api/*`)通信。后端内部按 `routes → controllers → services` 分层,职责边界清晰,便于定位问题和逐步扩展功能。

## 六、AI 辅助开发过程

### 使用的工具

Claude Code(Anthropic 官方 CLI Agent),全程用对话的方式提出需求、review 代码结构与设计决策,由 AI 完成具体编码实现。

### 我的协作方式(非技术背景视角)

我没有任何写代码和计算机背景,对 AI 来说是零基础的 Vibe Coding 用户。这个前提直接决定了协作方式:AI 默认使用者有一定基础,你不主动问,它不会主动补充说明。所以沟通中我需要经常问一些在有经验的人看来很基础的问题,也要在 AI 没有明确提出的地方主动追问"接下来还需要做什么"——比如环境搭建阶段,AI 指引我下载安装了 Git,但没有主动提"要不要把电脑和 GitHub 用 Token 连起来",是我追问之后才补上这一步,后续才能直接在 Terminal 里推送 commit,省去了很多手动操作。

正因为不懂代码、没法靠"读代码"来判断对错,我把最多时间花在了**前期框架搭建和需求梳理**上,目的是尽量把结构定清楚,减少后续返工的概率、提高容错率。具体做法是用对话的方式和 AI 一起梳理了我过往社媒运营工作里的完整流程和主要痛点,确定要做一个"流程管理系统",把最容易出问题的环节清晰地暴露出来,并且能沉淀成统计数据,支撑复盘和流程优化(详见「需求拆解阶段」和本 README 第一、二节)。

功能开发的节奏上,我要求先做出核心功能、能跑起来的真实页面,验证无误之后才继续推进更精进的功能,其余暂时不做的功能明确记录下来放到后面(见「后续规划」),不是一开始就贪多铺开。每一次 commit **之前**,我都要求 Claude 重新拆解这部分的实现原理、当面展示功能效果——这一步很关键:好几次都是在这个环节发现 AI 对之前写好的东西存在偏颇或错误的理解,如果不在这一步纠正,后面继续在错误理解上叠加功能,返工成本和浪费的 token 会呈指数增长。每一次 commit **之后**,我也会要求 Claude 复盘这一步做了什么、写清楚 commit 信息,再推送到 GitHub,确保每个环节都做到精细修改、不留遗漏。

核心功能全部做完并验证无误后,才开始做"让流程更高效"的锦上添花类功能(CSV 导入导出、看板图表化、界面美化等),期间同样是边测试边修改。项目基本完工后,我发现 README 是每次 commit 时增量更新的,大部分改动只是在之前内容上打补丁,时间久了出现了一些和实际实现脱节的明显错误,所以在整体开发完成之后,专门做了一次全局复盘,统一校对、修正、补全了 README。

### 需求拆解阶段

先由我(非技术背景,海外渠道营销岗位)用大白话描述实际工作中的痛点——素材等待没记录、审核打回历史没留存、Excel 排期表回答不了"卡在哪、卡多久、为什么"——由 AI 追问细化,整理成结构化的功能需求(见本 README 第一、二节)。在正式写代码前,AI 先输出了**项目目录结构方案**和**数据库表设计方案**(几张表、每张表的字段、表之间的关系),用非技术语言讲清楚"为什么这样设计"，我确认无误后才进入编码阶段。

### 开发过程记录

**阶段一(项目骨架搭建):**

- 做了什么:搭好前后端目录结构(`backend/` + `frontend/`),用 SQLite 建了 4 张表(内容主表 `contents`、状态历史表 `status_history`、审核记录表 `reviews`、打回原因表 `review_reject_reasons`),后端跑一个 Express 服务提供"健康检查"接口,前端用 React 写了一个能显示"是否连上后端"和"数据库里有几条内容"的验证页面。
- 为什么先做这步:这一步不产出任何用户能感知的功能,纯粹是为了在投入具体业务逻辑之前,先证明"前端 → 后端 → 数据库"这条链路是通的,后续每加一个功能都是在这个骨架上扩展,不用担心地基有问题。
- 中间遇到的问题:安装依赖时 `better-sqlite3`(数据库驱动)需要现场编译一段 C++ 代码才能在这台电脑上用,npm 出于安全考虑默认拦下了这类"安装时自动执行脚本"的行为,需要手动确认放行(`npm approve-scripts`)才能完成编译;另外前端依赖 `react-router-dom` 检查出安全漏洞,但当前阶段还没用到页面跳转功能,就先移除,等阶段二做多页面切换时再装无漏洞的版本。

**阶段二 1/2(内容录入):**

- 做了什么:后端加了一个"新建内容"的接口,前端做了一个真正能用的录入表单(平台、选题、内容类型等字段,下拉选项统一管理避免手填出现"Facebook"和"facebook"这种不一致的脏数据)。填完点保存,数据真的会存进数据库。
- 一个关键设计:创建一条内容的同时,后端会自动在"状态历史表"里补一条"进入选题环节"的记录,而且这两个写入动作放在同一个数据库事务里——要么两张表都写成功,要么都不写,不会出现"内容存了、但状态历史缺一条"这种半截数据。这样从内容被创建的第一刻起,状态历史就是完整的,阶段三做"状态流转"时不用回头补数据。
- 怎么验证的:不是"代码写完就当能用",而是真的启动服务、在浏览器里把表单填完点提交,然后直接连数据库文件查询,确认 `contents` 表和 `status_history` 表都正确写入了对应记录,截图和查询结果都保留在开发过程里。

**阶段三 1/2(状态流转 + 阻塞天数,后端):**

- 做了什么:新增"推进/回退状态"的接口,内置状态机规则校验——往后可以跳级(比如"选题"直接跳到"写文案"也允许),往前只有"审核"环节能退,而且能退回它之前的任意环节(不限定只能退一步),这两种情况在 `status_history` 里分别标记成"正常推进"和"审核回退",供后面看板统计"打回主要退到哪个环节"用。"阻塞天数"不存数据库,每次查询时用"当前时间 − 进入当前状态的时间"现算,已发布的内容不算阻塞。
- 遇到的问题和排查过程:第一次拿新表结构启动服务时报错"no such table: contents"。排查后发现是执行顺序的坑——`index.ts` 里 `import` 语句和"建表"函数调用虽然写在同一个文件,但 Node 按 `import` 出现的顺序依次执行,`import` 路由文件时会连带把 controller、service 文件也加载进来,而这些 service 文件在被加载的那一刻,顶层代码就会预编译 SQL 语句(`db.prepare(...)`);建表函数的调用语句虽然写在这些 `import` 后面,但那时候表其实还没建出来。之前两个阶段没暴露这个问题,是因为本地数据库文件从上一次就已经存在、表早就建好了,这次为了加新字段删了数据库文件重建,问题才第一次真正跑出来。修复方式:把"建表"这个动作放进数据库连接建立(`connection.ts`)的那一刻立刻执行,不再依赖其他文件按什么顺序 import,保证任何模块只要连上数据库,表就已经存在。
- 怎么验证的:用接口把状态机规则挨个测了一遍——正常推进、跳级推进、审核退回任意更早环节、非法回退(非审核状态倒退)、目标状态和当前状态相同、"发布"后不能再变、内容不存在,一共 7 种场景,每种都确认返回结果(成功 or 具体错误信息)符合预期;还手动把"进入当前状态时间"改到 5 天前和 10 天前,验证阻塞天数算得对、已发布内容不算阻塞。

**阶段四 1/2(审核记录 + 打回原因,后端):**

- 做了什么:新增"提交审核"接口——语言审核(英语母语者)经常在文案/制作阶段就提前审一遍,所以"写文案""制作""审核"三个环节都能提交审核记录;但只有内容当下正处于"审核"环节时,打回才会连带触发状态回退(退到哪个环节由提交人指定),这两件事(记审核 + 变状态)在同一个数据库事务里完成。"第几轮"不用手填,系统自动数这条内容之前提交过几次审核再 +1。
- 遇到的问题和排查过程(一个真实 bug):测试"打回但退回目标不合法"这个场景时,我故意把退回目标设成"排期"（"审核"之后的环节,顺序上不算"退回"），结果接口居然返回成功,内容状态真的被改成了"排期"。排查后发现:校验函数 `validateTransition('审核', 目标状态)` 判断的是"这个状态变化本身合不合法",而"审核"往后走到"排期"本来就是合法的正常推进——它没有区分"这次调用的语义是打回"和"这次调用的语义是正常推进"，所以一个只往后走的目标状态被当成"合法的打回"放行了。修复方式:在调用这个通用校验之前，先显式检查退回目标必须严格早于"审核"在流程里的位置(选题/收集素材/写文案/制作这四个之一),把"排期""发布""审核"自己这些不该出现在打回选项里的值挡在前面。这个 bug 能被发现,是因为验证清单里专门设计了"故意传一个不合法的值"这一类测试用例,不是只测正常情况。
- 怎么验证的:一共测了 9 种场景——写文案阶段提前打回(应成功但不改状态)、审核环节通过(应成功且不自动改状态)、审核环节打回联动回退(应成功且状态和 status_history 都正确变化)、非可审核状态提交(拒绝)、打回不给理由(拒绝)、审核打回不给退回目标(拒绝)、退回目标不合法即"排期"(拒绝，这个是上面提到的 bug)、审核角色不合法(拒绝)、内容不存在(拒绝);还确认了轮次自动累加、失败请求不会产生任何副作用(数据库状态在失败后原样不变)。

**阶段六 1/3(CSV 导入,后端):**

- 做了什么:新增导入接口，能批量把 CSV 文件里的内容一次性存进数据库。两个关键的数据正确性问题:(1) 编码——Excel 导出的 CSV 可能是 UTF-8(常带 BOM 头)也可能是中文版 Excel 默认的 GBK,处理方式是先剥掉 BOM,再尝试严格按 UTF-8 解码,解码失败就自动改用 GBK,两种情况都能正确读出中文,不会乱码。(2) 部分行有问题不该拖累整批——每一行独立校验、独立写入,校验不过的行(比如"发布平台"为空)会被跳过并记录具体原因,其余行照常导入成功。
- 一个跟"能不装依赖就不装"原则不一样的决定:CSV 解析(尤其是处理带逗号的文本字段,比如选题里写"设备保养提示,含逗号")和中文编码转换，自己手写很容易在边界情况下悄悄读错数据、导致真实业务数据被污染，所以这次装了两个成熟的专门库(`csv-parse` 解析 CSV、`iconv-lite` 处理 GBK 解码)——路由库、图表库是"有更简单的替代方案就不用装"，但数据正确性上该装还是要装,两种场景判断标准不同。
- 怎么验证的:构造了两份内容完全一样、但编码不同的测试 CSV(一份 UTF-8+BOM，一份 GBK)，分别导入后查数据库确认中文内容都正确、不乱码;构造了一份带逗号的选题文本，确认没有被逗号错误拆成两列;构造了几行故意缺"发布平台"或"选题"的数据，确认这几行被正确跳过且原因提示准确，其余行正常导入;还测了完全不是 CSV 格式的畸形内容(未闭合的引号)，确认接口给出清晰报错、服务器没有崩溃。

**阶段七 1/2(复盘数据录入入口):**

- 做了什么:发现一个之前没意识到的功能缺口——`曝光量/点赞/评论/转发/私信数/涨粉数`这些复盘字段虽然数据库有、看板也在用，但整个系统里没有一个表单能让用户手动填这些数字，唯一的数据来源是种子脚本。这次补上了:详情页新增"复盘数据"表单(只有内容处于"发布"状态才显示)，支持反复打开、覆盖式更新(发布24小时后填一次、7天后再填一次都可以，每次都会重新记录`metrics_captured_at`)。顺带加了"收藏数"(`saves`)字段，之前设计的复盘字段里没有这一项。
- 一个统计准确性上的关键处理:表单里每个数字字段留空就是留空，不会被偷偷当成 0。原因是不同平台能采集到的指标不一样(比如 Facebook 基本没有"收藏"功能)，如果拿不到的指标存成 0，会拉低这个平台的平均值、得出错误结论。SQL 的 `AVG()` 函数本身就会自动跳过 NULL 不参与计算，所以只要保证"没填"存成 NULL 而不是 0，看板统计就自然是对的，不需要额外的过滤逻辑。种子数据里特意让 Facebook 相关内容的"收藏数"留空(模拟真实情况)，用来验证这一点。
- 怎么验证的:后端先用接口测试——正常状态(非"发布")下提交复盘数据应被拒绝；发布状态下只传一个字段、其余留空，查库确认其余字段正确存成 NULL；直接查 `AVG(saves)` 按平台分组，确认 Facebook 那一组返回 `null` 而不是被少数几条数据拉出一个奇怪的 0 附近的值。再通过浏览器走了一遍真实表单流程:打开一条 Facebook 已发布内容，确认"收藏"字段是空的(不是 0)、其余字段正确用现有数据回填，提交后查库确认数据完整保留、收藏数依然是 NULL、`metrics_captured_at` 正确刷新。

**阶段七 2/2(平台效率对比看板):**

- 做了什么:看板新增"平台效率对比"——按"平台 × 内容目标"交叉分组(比如 4 个平台 × 4 类目标最多 16 组)，展示每组的平均曝光/点赞/评论/转发/收藏/私信/涨粉。这跟已有的"各内容目标效果"是两个不同切面:后者只按内容目标分组、不分平台，回答"不同目的的内容效果好不好"；新的这个按平台再拆一层，回答"同样类型的内容，发在不同平台上效果差多少"。顺手把"各内容目标效果"原本用 `impressions IS NOT NULL` 判断"是否有复盘数据"的写法，统一改成用 `metrics_captured_at IS NOT NULL` 判断——因为不同平台能采集的指标不一样，用某个具体指标是否为空来筛选，会漏掉"填了别的指标、但这个指标恰好没有"的内容。
- 怎么落实"样本量不足要提醒"这个要求:每组返回的数据里带一个 `sample_size`(这组有几条内容)，前端在样本数小于 3 的分组，表格里直接标"n=X + 数据不足，仅供参考"的黄色警示，而不是让用户自己数有几条、自己判断能不能信。这批种子数据每组样本数大多是 1，正好完整展示了这个提示——现实中数据量不够大的时候，这种提醒能防止把偶然结果当成规律。
- 怎么验证的:直接查库手算 Facebook · 品牌曝光这一组(2条已发布内容)的平均曝光量、平均点赞，跟接口返回的数字精确对上；确认这一组的"平均收藏"返回 `null`(这两条都是 Facebook,收藏数种子数据里就没填)，没有被错误拉成 0 附近的值；用完整的页面 DOM 结构核对(不只是看截图)，确认"n=2""数据不足，仅供参考"这些文字精确出现在对应的单元格里，跟接口数据一一对应。

**阶段八(素材等待统计看板):**

- 做了什么:看板新增"素材等待统计"，只看"收集素材"这一个环节，按素材来源(`material_source`)分组，回答"平均要等几天""哪个供应方经常拖"。用 `status_history` 表里"进入收集素材"和"离开收集素材"两条记录的时间差算出每一次等待的时长——技术上用了 SQL 的 `LEAD()` 窗口函数，在同一条内容完整的状态历史里，找到每一次"进入收集素材"后紧跟着的下一条记录，两者的时间差就是这次等待时长。
- 一个统计设计上的关键调整(来自我的提醒):最初设计打算只统计"已经结束的等待"，被指出这样会有幸存者偏差——等得最久、最有问题的那些(比如某个供应方拖了很久还没交)恰恰是还没结束的，一旦被排除在平均值之外，统计出来的"平均等待天数"会显得很健康，但真正最严重的问题反而被藏起来了。改成了"已完成等待"和"进行中等待"分开展示、不合并成一个数字:前者是平均天数+样本数(带"数据不足"提示)，后者是当前有几条在等+这批里最长等了多久，不套"数据不足"提示——因为后者不是在算平均值，只是陈述"现在有几条、最长等了几天"两个客观事实，哪怕只有 1 条也是真实发生的事，不存在"数据不够所以不可信"的问题。素材来源没填的内容不会被丢弃，单独归到"未填写"一组，这本身也是一个值得关注的信号。
- 怎么验证的:种子数据本身没有模拟完整的多段状态历史(阶段一就已经在代码注释里说明了这个简化)，所以没法直接拿种子数据验证"已完成等待"这部分逻辑。专门手动构造了一批测试用的 `status_history` 记录——两条内容都归到"供应方A"，等待时长分别是 4 天和 6 天，验证接口返回 `avg_wait_days = 5`(即 (4+6)/2)，精确对上;另一条内容单独归到"供应方B"，等待 20 天，验证返回 `avg_wait_days = 20` 且样本数=1(应该触发前端"数据不足"提示)。验证完把这些测试数据清理掉、恢复成正常种子数据。"进行中等待"部分则直接用种子数据验证，3 条正处于"收集素材"状态的内容被正确分到各自的素材来源分组（包括没填来源的那条被正确归到"未填写"）。

**阶段九(界面美化，独立分支 `ui-polish`):**

- 做了什么:这一步不涉及新功能，只重做视觉。给了我一张参考截图(TailAdmin 风格的后台看板)，提炼出三个方向:圆角更大、颜色更克制(不用高饱和度撞色，走中性灰+一个商务蓝主色)、层级分明(数字靠字号字重传达重点，不是靠颜色)。具体做法:
  - 建了一套 CSS 变量(设计 token)——中性灰阶、主色、语义色(成功绿/警示琥珀/危险红)、圆角、间距、字号，全部样式改成引用变量，不再有硬编码的颜色值散落在各个组件样式里。
  - 状态标签重新梳理语义:默认状态是中性灰，只有"发布"(成功，绿色)和"阻塞"(警示，琥珀色)两种真正需要提醒的状态才上色，而不是每个状态硬凑一个颜色。审核"打回"和状态"回退"也统一成警示色而不是危险红——这两种情况是正常的编辑流程事件，不是系统报错，用刺眼的红色不合适，红色留给真正的表单校验错误。
  - 看板"当前阻塞内容数"这类数字，不再整个染成红色——改成数字保持中性深色(用字号本身传达重要性)，前面加一个小圆点提示，避免看板"花"，数字才是主角。
  - 状态时间线和审核历史列表，从"一坨横排文字紧挨着堆一起"改成左侧竖线+圆点的时间轴样式，一眼能看出这是按时间顺序排列的记录。
  - 结构上的调整:"批量导入"不再是顶层导航的一个独立 tab(它本质上是"录入内容"的另一种方式，不是一个独立的主功能)，收进"录入内容"页面右上角的一个小按钮，导航从 4 个 tab 精简到 3 个，主流程更聚焦。
  - 这次改动几乎全部集中在 `global.css` 一个文件里——因为所有页面已经在共用同一套 class 名，改一处设计 token 能级联到全部页面，不需要逐个组件改 JSX，效率更高。
- 怎么验证的:用浏览器实际走了一遍主要页面，重点核对了几处容易"看着改了、其实没改对"的地方——用 DOM 结构直接读取计算后的样式值，而不是只看截图:确认阻塞行的背景色是新定义的琥珀色(而不是残留的旧红色)、阻塞标签文字颜色对应新的警示色变量、看板"阻塞数"大数字本身是中性深色只有一个小圆点是彩色的、时间线每一条都有竖线+圆点(且列表最后一条的竖线正确收尾)。结构改动方面，实测点击"批量导入 CSV"按钮能正确切换到导入页面、"返回手动录入"能切回来，且切换过程中顶部导航"录入内容"始终保持高亮(因为这两个视图算同一个主功能下的二级切换)。
- 这一步在独立的 `ui-polish` 分支上做，不直接改 `main`，出问题可以随时丢弃分支回退，不影响已经稳定的功能代码。

**顺手修的一个真实可用性问题:** 看界面的时候发现内容列表的筛选栏里没有"是否阻塞"这个选项，想看当前有哪些内容卡住了，只能一页页往下翻着找。加了一个"只看阻塞内容"勾选框——因为"是否阻塞"本来就是查询那一刻现算出来的、已经跟着每条记录一起返回了，所以这个筛选直接在前端已经拉到的数据上做即时过滤，勾选框一点立刻生效，不用再点"筛选"按钮、也不用多请求一次后端接口。验证方式:实测勾选后列表从 28 条立刻收窄到 3 条，跟看板"当前阻塞内容数=3"对得上；点"重置"确认勾选框和列表都正确恢复。

**看板部分数字改成图表展示:** 用户反馈"只有数字堆着不直观，能不能做成图表"。这里区分了两种情况处理，不是所有表格都改：
- **发布节奏(按平台)、素材等待统计**——这两块本质是"一个类别对应一个数字"(比如"Facebook 完成率33%"、"某供应方平均等5天")，跟已有的条形图(`BarList`)结构完全一样，改起来风险很低，于是把原来的表格换成了条形图，条形宽度表示数值大小，右侧文字保留具体数字方便看细节(比如"3/9 · 33%")。为此把 `BarList` 组件扩展了一下，支持自定义右侧显示文字(`displayValue`)和固定的比例基准(`max`，比如百分比类指标要固定按 100 算比例，不能跟着数据大小浮动)，向后兼容，原来的用法不用改。
- **各内容目标效果、平台效率对比**——这两块特意保留了表格，没有强行改成图表。原因:这是"多个类别 × 7 个指标"的密集交叉对比，指标之间数量级差异很大(曝光量是几万、私信数是几十)，硬塞进一张图会让小数值的指标在图上完全看不清；而且这批数据大部分分组样本量只有 1-2 条("数据不足"警示基本每行都有)，把统计上不可靠的数字画成醒目的图表反而容易让人过度解读、误以为差异很明显。这种"多指标密集对比"场景表格本来就是更诚实的呈现方式，不是技术做不到，是特意不做。
- 怎么验证的:改完后用种子数据实际看了一遍，"发布节奏"四条平台的条形图长度比例(33%/38%/29%/25%)跟数字标签、跟之前手算验证过的完成率一致；"素材等待统计-进行中"条形图的"最长天数/当前条数"文字跟接口数据一一对应。

### 典型的方案调整案例

以下按开发时间顺序,记录六处由我(非技术背景,基于真实海外社媒运营工作经验)提出、AI 据此修正技术方案的案例。统一格式:AI 最初方案 → 我基于什么场景提出异议 → 最终怎么调整 → 带来什么价值。

**1. 打回原因是否支持多选(数据库设计阶段,阶段一之前):**
- AI 最初方案:设计 `reviews` 表结构时,`reject_reason` 是单个字段,一条审核记录只能记一个打回原因分类。
- 我的异议:实际审核中,一轮反馈经常同时指出多个问题(比如"语法错误"+"配乐太吵"+"内容冗余"),只能存一个会让"打回原因分布"这个统计失真。
- 最终调整:拆出一张独立的 `review_reject_reasons` 表,一条审核记录可以对应多个打回原因(一对多关系),前端做成可多选的勾选框。
- 带来的价值:打回原因分布统计不再因为"一次打回只能记一个理由"而失真,能更准确地定位返工的根本原因集中在哪一类问题上。

**2. 审核回退范围 & 是否允许跳级(阶段三):**
- AI 最初方案:"审核"环节打回只能退回紧邻的"制作"或"写文案"这两步;正常推进只能走到相邻的下一个环节,不能跳级。
- 我的异议:(1) 老板审核关注的是内容方向,方向错了退回改文案没用,得从选题重来;"受众适配"类打回往往是选题/受众定位的问题,不是制作环节的问题,退回范围要覆盖到审核之前的所有环节。(2) 工作中经常有内容不需要经过某些环节(比如已有素材库、不用重新收集素材),不该强制"只能走下一步"。
- 最终调整:审核可以退回到它之前的任意环节(选题/收集素材/写文案/制作);正常推进允许跳级。`status_history` 新增 `transition_type` 字段区分"正常推进"和"审核回退"。
- 带来的价值:状态流转规则贴近真实工作场景;区分"推进"和"回退"两种类型,让看板能统计"打回主要退到哪个环节",直接支撑"是选题对齐问题还是制作环节问题"这类流程改进判断。

**3. 审核记录提交入口的开放范围(阶段四):**
- AI 最初方案:只有内容处于"审核"这一个环节时,才允许提交审核记录。
- 我的异议:实际工作中语言审核(英语母语者)经常在文案完成后就提前过一遍,这时候内容还在"写文案"或"制作"状态,等到正式"审核"环节才能提交意见,等于逼着语言问题拖到最后才暴露。
- 最终调整:把可提交审核记录的范围扩大到"写文案""制作""审核"三个环节,但只有内容真正处于"审核"环节时,打回才会联动触发状态回退——提前审核只是记录问题,不代表流程要真的往回走。
- 带来的价值:语言问题能更早被发现和记录,不用等到审核环节才暴露;同时状态回退的语义保持清晰,不会因为提前审核的打回而误触发不必要的流程倒退。

**4. 复盘数据的空值处理(阶段七前置讨论):**
- AI 最初方案:讨论"平台效率对比"这个看板功能时,只提出"按平台/内容目标分组算平均值",没有主动说明"某个指标没有数据"时该怎么处理。
- 我的异议:不同平台能获取的指标本来就不一样(比如收藏数在 Instagram 有、Facebook 基本没有这个功能),如果拿不到的指标存成 0,会拉低这个平台的平均值,得出"这个平台效果差"的错误结论。
- 最终调整:复盘数据表单里,数字字段留空就存成数据库的 NULL,不当成 0;SQL 的 `AVG()` 函数天然会跳过 NULL、不参与计算,不需要额外写过滤逻辑。种子数据里也特意让 Facebook 的"收藏数"留空来验证这一点。
- 带来的价值:避免"某平台因为统计口径缺陷被系统性低估"这种偏差,平台之间的效果对比更可信。

**5. 交叉分组的样本量提示(阶段七前置讨论):**
- AI 最初方案:"平台效率对比"最初的设计只有"按平台 × 内容目标交叉分组算平均值",没有考虑分组之后每组实际有多少条数据。
- 我的异议:平台 × 内容目标是 4×4=16 个分组,以当时的数据量,很多分组可能只有一两条样本,直接展示平均值容易让人把偶然结果当成规律。
- 最终调整:每个分组的统计结果都带上 `sample_size`(样本数),前端在样本数小于 3 的分组标注"数据不足,仅供参考"的警示样式;这个规则后来也统一应用到"素材等待统计 - 已完成等待"这个同样存在小样本问题的模块。
- 带来的价值:防止把统计上不可靠的偶然结果误读成规律性结论,这是数据可视化里一个容易被忽视、但很实际的陷阱。

**6. 素材等待统计是否排除"进行中"的等待(阶段八前置讨论):**
- AI 最初方案:只统计"已经结束的等待"(进入、离开"收集素材"两个时间点都有记录),还没结束的等待不计入平均值——理由是时长还在变化,混进去会让数字失真。
- 我的异议:排除未完成的等待会造成幸存者偏差——等待时间最长、最有问题的那批(比如某个供应方拖了 20 天还没交)恰恰是还没结束的,一旦排除,平均值会显得很健康,但实际上最严重的问题被藏起来了。
- 最终调整:改成"已完成等待"和"进行中等待"分开展示、不合并成一个数字:前者算平均天数(带样本量提示),后者展示"当前有几条在等 + 最长等了多久"两个客观事实,不套用"数据不足"提示(这不是在算平均值,哪怕只有 1 条也是真实发生的事)。
- 带来的价值:看板不会把最严重的问题(供应方长期拖延)藏在健康的平均数背后,能真实反映"现在到底谁在拖",这正是运营决策(该催谁、该不该换供应商)最需要的信息。

## 七、后续规划

以下功能是明确考虑过、但基于时间和优先级主动没做的,列出来说明取舍的理由:

- **多次数据抓取快照(`performance_snapshots` 表)。** 现在的复盘数据(曝光量、点赞等)是覆盖式更新——一条内容对应一份"最新"复盘数据,更新一次就覆盖上一次,不保留历史轨迹。如果要支持"同一条内容发布 24 小时和 7 天后的数据对比"这种更细的分析,需要单独建一张快照表,一条内容对应多条按时间点存的复盘数据。数据库表结构在阶段一设计时已经预留了这个扩展空间(复盘字段直接放在 `contents` 表里,而不是耦合进其他表),加这张表不影响现有结构,但当下优先把"核心流程能跑通"做完整,这个更细粒度的分析先不做。
- **用户账号体系与权限管理。** 现在系统没有登录、没有账号,"负责人""审核人""操作人"这些字段都是自由文本(手动填名字),不是真实的用户账号,任何人打开系统都能操作任何内容,没有权限区分。这是一个单人/小团队内部工具原型,优先做完"业务流程能不能被完整记录和追溯"这个核心问题,账号体系属于"让工具能被多人安全共用"这一层,是下一步如果要真正上生产环境才需要解决的问题。
- **平台 API 自动同步复盘数据。** 曝光量、点赞、评论这些数据现在需要运营人员手动填进"复盘数据"表单,没有对接 Facebook/Instagram/LinkedIn/YouTube 的官方 API 自动拉取。手动录入这一步本来就是当前 Excel 排期表的痛点之一,自动同步是更长远的改进方向,但每个平台的 API 申请、鉴权、限流规则都不一样,工作量和维护成本远超这次项目的范围。
- **发布节奏的断更预警。** 最初设想过"某平台连续多少天没有发布内容就提醒"这类主动预警,现在的"发布节奏"看板只做了"计划数 vs 已发布数"的完成率统计,没有做成主动提醒。等通知机制(比如邮件/企业微信提醒)这类基础设施做了之后,可以在现有数据基础上加这层判断逻辑,不需要改动数据模型。
- **中英双语界面。** 界面文字目前是中文,内容数据本身(选题、文案)是自由文本,可以直接填英文。真正的双语切换需要把所有界面文案改成从语言字典读取、再加一个语言切换开关,是一次系统性改动,不是简单翻译。评估过后决定放在明确有需要(比如要给只懂英文的人演示或操作系统本身)的时候再做,详见开发过程记录。
